# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Purpose

.NET 10 console app (batch) that acts as a **clinical simulator** for an OpenMRS instance. It generates realistic patient records, visits, encounters, observations, orders, and allergies that reflect a real-world clinic workflow — driven by a probabilistic epidemiological model parameterized by age and gender.

## Build & Run

```bash
dotnet build openmrs_seeder_v1/openmrs_seeder_v1/openmrs_seeder_v1.csproj
dotnet run --project openmrs_seeder_v1/openmrs_seeder_v1/openmrs_seeder_v1.csproj            # corre la simulación completa y termina
dotnet run --project openmrs_seeder_v1/openmrs_seeder_v1/openmrs_seeder_v1.csproj -- clear   # anula los datos SIM- (pide confirmación s/N)
dotnet test
```

**Console batch app (no web server)** since `develop2`: `dotnet run` executes the whole simulation per `appsettings.json` and exits. La corrida se estructura en **4 etapas** (`Program.cs`): **1/4 validación de catálogos** (filas cargadas de los 15 CSV, opcionales vacíos marcados como desactivados, advertencias, y aborto con exit 2 si hay errores — ver *Catalog validation*), **2/4 días a simular** (ventana, días con atención vs. cerrados por `WeekdayWeights`, volumen previsto total/nuevos/recurrentes y desglose **por día** si son ≤31 días con atención o **por mes** si son más), **3/4 ejecución** — precedida de una **pausa de 5 s** (`PausaPreviaSegundos`) para poder abortar con Ctrl+C antes de la primera escritura — con progreso cada ~15 s, y **4/4 resumen final**, que **espera una tecla** para terminar (`EsperarTecla`) y así no se pierde si la terminal se cierra al salir. El resumen se nutre de `Services/RunStats.cs` (singleton, acumulador puro testeado en `RunStatsTests`, alimentado desde `SeedOrchestrator.ProcesarVisitaAsync` **solo con las visitas realmente creadas** en OpenMRS, y reseteado al inicio de cada corrida): visitas totales separadas en **nuevos vs. recurrentes**, pacientes distintos + cuántos **volvieron** (≥2 visitas) + media de visitas/paciente, **visitas por semana** (agrupadas por el lunes que la abre, `RunStats.InicioDeSemana`, sin depender de la cultura) y **top 5 diagnósticos** (primarios + comorbilidades, con nº de diagnósticos distintos usados — indicador de la variedad real del catálogo; los % son sobre las visitas y pueden sumar >100 % porque una visita puede llevar varios dx). Además: etapa, días simulados, ventana sembrada, duración y errores de proceso/operación. ⚠️ La espera se omite si `Console.IsInputRedirected` (Docker, CI, salida a fichero → colgaría el proceso) o si se canceló con Ctrl+C. El plan de días lo cachea `SeedOrchestrator.PlanificarDias()` y lo reusa `RunAsync`: ⚠️ `DailyScheduleGenerator` comparte su RNG con las horas de visita, así que regenerarlo para el informe desplazaría el flujo aleatorio y el informe describiría una corrida distinta de la que se ejecuta. Exit codes: 0 = completed, 1 = process failure (`etapa error`), 2 = OpenMRS unreachable / bad CLI arg. Ctrl+C cancels cleanly (inserted data persists). The old Web API + Swagger version lives in `develop1`.

## Architecture

**The simulator connects to OpenMRS exclusively via REST API** (`/ws/rest/v1`). It does NOT write SQL directly. All data is inserted through OpenMRS REST endpoints (POST /patient, POST /visit, POST /encounter, POST /obs, POST /order, POST /patient/{uuid}/allergy).

Key architectural decisions:
- **Simulator model**: daily patient volume is driven by `PacientesPorDiaMedio` + weekday weights + normal distribution. Each patient gets a diagnosis chosen from `epidemiology-profile.csv` weighted by age/gender.
- **Catalog-driven coherence**: diagnoses, labs, medications, clinical exams, and allergies are selected from CSV catalogs using boolean columns (`aplica_CATEGORIA`, `aplica_GRUPO_EDAD`) — no hardcoded lists. **13 categories**: respiratorio, cardiovascular, diabetes, digestivo, osteomuscular, urologico, infeccioso, endocrino, neurologico, dermatologico, salud_mental, ginecoobstetrico, trauma. ~950 diagnoses (a broad pool: ~125 hand-curated common+critical with calibrated weights + ~575 harvested variants + ~246 Centroamérica-specific entries —dengue, chikungunya, zika, etc.— deduped by name into the single `diagnosticos.csv`; low-weight rows so the common ones still dominate). Adding a category = new `aplica_<cat>` column in medicamentos/laboratorios/examenes models + `CatalogLoader` + the `AplicaCategoria` switch in ConsultaSeeder/LabOrderSeeder/PrescriptionSeeder + epidemiology-profile rows + (optionally) a row in `comorbilidad_afinidades.csv` (DiagnosticoEntry uses a `Categoria` string, so diagnoses need no model change).
- **⚠️ Verify every CIEL UUID against THIS instance** via `GET /concept?q=`. Many UUIDs in the original catalog were wrong (recorded a different disease while still being valid concepts, so no error surfaced) — e.g. `117321` is *hipotiroidismo* not HTA, `116128` is *paludismo* not fiebre. All diagnosis UUIDs were re-verified; do the same for any new entry. Imaging/EKG are ordered as **test orders** (no procedure order type in this instance).
- **Seeder pipeline**: each domain is a self-contained seeder (`PatientSeeder`, `AllergySeeder`, `VitalsSeeder`, `ConsultaSeeder`, `LabOrderSeeder`, `PrescriptionSeeder`, `VisitCloseSeeder`) coordinated by `SeedOrchestrator`.
- **Batch execution**: the process IS the run — `Program.cs` awaits `SeedOrchestrator.RunAsync` in the foreground; `SeedProgressTracker` (in-memory) is still the progress source, consumed by a `PeriodicTimer` console reporter instead of a `GET /progress` endpoint. There is no controller layer (removed with the API).
- **Precise error counting (`ErrorTally`)**: seeders swallow per-item failures (a rejected obs, a failed order) with `LogError` + continue, so the tracker's `Errores` (process-level) said "0 errores" while items were silently lost. `Services/ErrorTally.cs` + `ErrorTallyLoggerProvider` (registered in `Program.cs` logging pipeline) count every Error-level log by component (last segment of the logger category) — no seeder changes needed, future seeders included. Progress/final summary report **errores de proceso** (tracker) and **errores de operación** (tally, with per-component breakdown + truncated messages, cap 100). Item errors don't change the exit code (still 0). Tested in `ErrorTallyTests`.
- **Idempotency**: all seeded patients have identifier prefix `SIM-`; visits/encounters have `SEEDED_BY_SIMULATOR` in description. `dotnet run -- clear` (logic in `Services/DataCleaner.cs`, asks for console confirmation) voids them all.
- **Dual identifier**: patients get an OpenMRS ID (Luhn Mod-30 valid) + "Old Identification Number" with `SIM-` prefix for tracking.
- **Same-day deduplication**: `SeedOrchestrator` uses a `HashSet<string>` of OpenMrsUuids per day so a patient cannot appear as both new and recurring on the same day.
- **Comorbidity (multimorbidity per visit)**: after the primary diagnosis, `EpidemiologySelector.SelectComorbilidades` may add 1..N extra diagnoses (config `Simulation.Comorbidity`). Probability scales with age (`AgeScaling`) and the extra category is weighted toward clinically-related clusters (`comorbilidad_afinidades.csv` × `AffinityBoost`). All diagnoses land in one encounter; `LabOrderSeeder`/`PrescriptionSeeder` filter catalogs by `patient.Categorias` (union of all diagnoses' categories) so labs/meds stay coherent across comorbidities.
- **Diagnosis variety (anti-repetition damping)**: without it, high-weight dx monopolize selection and only ~30% of the ~950-dx catalog ever appears. `Simulation.Variedad.RepeticionDamping` (default 0.25, 0 = off): every time a dx is picked in the run, its effective weight decays (`peso / (1 + damping × usos)`, pure seam `EpidemiologySelector.PesoConDamping`, per-run counters reset via `ResetUsos()` from `SeedOrchestrator.RunAsync`). The epidemiological profile is untouched (category selection by age/sex/climate is not damped) and chronic/acute control visits (deliberate repetition) bypass the selector entirely. Complemented by widening the `comun=true` pool in `diagnosticos.csv` from 189 → 242 rows (criterion extended to `max(peso) >= 8 && severidad != grave`). Measured (1-month runs, ~345 visits each): distinct dx **144 → 182**, top-10 share **31.3% → 17.2%**, most-repeated dx 20× → 8×.
- **Two-stage diagnosis selection (common-disease bias)**: each **run** draws its common-probability once via `EpidemiologySelector.DrawRunCommonProbability()` uniformly in `[Simulation.CommonProbMin, CommonProbMax]` (default 0.75–0.95), so the common share **varies run-to-run** but always leans common. Per patient, `RollPreferCommon(runProb)` decides the pool; the primary `SelectCategoria`/`SelectDiagnostico` then restrict to it via the `comun` column (precomputed `_categoriasPorComun`, same pattern as `_categoriasPorClima`), with fallback if a pool is empty. Stage 2 keeps the existing category/weight/clima logic. Comorbidities are unaffected. `comun` is derived from existing weights (`max(peso_M,peso_F) >= 10 && severidad != grave`).
- **Seasonal climate (optional)**: if `catalogs/clima.csv` exists (per ISO week → `estacion` + `temp_promedio_c`), `ClimateResolver` maps each visit's date to its season. `EpidemiologySelector` multiplies by `Climate.SeasonalBoost` the weight of categories/diagnoses tagged with that season (`clima` column in `diagnosticos.csv`, e.g. gripe→invierno, dengue/EDA→verano,lluvia), and `VitalsSeeder` nudges body temperature up in hot weeks (heat only). Absent file / unlisted week / `Enabled=false` → neutral. `climate` is an optional last param on the selector methods so behavior is unchanged when null.
- **Allergies (probabilistic prevalence + conditional count)**: `AllergySeeder` only seeds **new** patients (registered once at first visit). Like the common-disease bias, each **run** draws its allergy prevalence once, uniformly in `[Allergy.BaseProbabilityMin, BaseProbabilityMax]` (default 0.15–0.25 — the clinically-documented fraction of the ~25-30% real population prevalence), so the allergic share varies run-to-run. For patients who *are* allergic, the **number** of allergies uses conditional decay (same shape as comorbidity): everyone gets ≥1, a 2nd is added with `SecondAllergyProbability`, a 3rd (only if 2) with `ThirdAllergyProbability`, capped by `MaxAllergies` and catalog size — so most have 1, few 2, rare 3 (vs. the old uniform 1–3). Count logic is the pure testable `AllergySeeder.DecidirCantidad`.
- **Dynamic location & staff (consultorios + médicos)**: `ClinicResourceAssigner` (registered transient, called once per run from `SeedOrchestrator.RunAsync`) makes data realistic across multiple consultorios instead of a single "Unknown Provider"/stale location. Catalog `consultorios.csv` (`location_uuid,medico_identifier,medico_nombre`) lists each consultorio + médico (read via `CatalogLoader.Consultorios`). `InitializeAsync` **idempotently** ensures each médico exists (`GET /provider?q={identifier}` exact-match → else `POST /person` with `medico_genero` then `POST /provider`) and is **fail-fast**: if any catalog médico can't be ensured it throws (pure `ResolvePool`), so the run aborts in `error` state *before* creating data (no encounters under "Unknown Provider"). Empty `consultorios.csv` = no throw, single-provider fallback. Per visit, `ProcesarVisitaAsync` calls `AssignVisit(patient, citaRecursos)` — con los recursos de la cita si el paciente viene a su control (se honran sin re-sortear), `null` en caso contrario; every seeder uses `patient.Assigned… ?? _settings.Defaults.…` (so empty `Consultorios` = old single-resource behavior). **Médico de cabecera**: new patients draw a random consultorio that becomes their `CabeceraLocationUuid/CabeceraProviderUuid` (recurrent patients inherit it from the pool); a recurrent visit returns to that same médico with a **per-run probability** drawn uniformly in `[Simulation.MedicoCabeceraProbMin, Max]` (default 0.70–0.90, leans yes, like `CommonProbMin/Max`), else lands with another médico. Pure decision seam `ClinicResourceAssigner.UsarCabecera`. Patient registration uses `Defaults.RegistrationLocationUuid` (Recepción), not a consultorio. Médicos are reference data: `SIM-MED-*` identifiers, reused across runs, **not** voided by the `clear` subcommand. Pure `ClinicResourceAssigner.Pick` is the testable seam. (Billing/cashier is NOT installed in this instance — out of scope.)
- **Problem list (conditions)**: `ConditionSeeder` runs after `ConsultaSeeder` and adds each diagnosis flagged `cronica=true` (HTA, diabetes, EPOC, hipotiroidismo, epilepsia, ERC, depresión, VIH, artritis…) to the patient's problem list via `POST /condition`. Deduplicated per patient via `SimulatedPatient.ProblemListConcepts` (shared across recurrent visits, like `OrderedConcepts`).
- **Program enrollment (programas de atención)**: `ProgramEnrollmentSeeder` runs after `ConditionSeeder` (same chronic-driven trigger) and enrolls the patient in an OpenMRS care program via `POST /programenrollment` when a diagnosis (by UUID) or category matches the new catalog `programas.csv` (`program_uuid,program_nombre,trigger_dx,trigger_categoria,estado_inicial_uuid`). Deduped per patient via `SimulatedPatient.EnrolledPrograms` (shared across recurrent visits, like `ProblemListConcepts`). Pure seam `ProgramEnrollmentSeeder.SeleccionarProgramas`. Optional initial workflow state (`estado_inicial_uuid` → `states:[{state:"<uuid>",startDate}]`, plain-string state). **Programs are instance-specific — verify with `GET /program?v=full`.** Verified in THIS instance: HIV Care and Treatment (`64f950e6-…`, state "On Antiretrovirals Treatment" `7c0a5653-…`) ← VIH dx `149197…`; Outpatient Diabetes Education Program (`7a72a724-…`, no workflow) ← category `diabetes`. Empty/absent catalog = inactive. `/clear` doesn't explicitly void enrollments (like conditions/allergies — inaccessible once the patient is voided). Tested in `ProgramEnrollmentSeederTests`.
- **Follow-up (nota de seguimiento)**: en `ConsultaSeeder`, la probabilidad de agendar control es **condicionada al cuadro** vía el seam puro `SeguimientoPolicy.Probabilidad(dxs, ReferralProbabilities)` (crónico `FollowUpCronico` 0.90 → grave `FollowUpGrave` 0.80 → resto `FollowUp` 0.30). Si dispara, la fecha sale de la **banda de recurrencia** (`RecurrenceScheduler.ProximaFechaElegible`, agudo 7–21 d / crónico 30–120 d), NO de un 7–30 plano; se registra la obs **fecha** "Return visit date" (`5096AAAA…`, datatype Date) y la fecha queda en `SimulatedPatient.FechaSeguimiento` para que `FijarProximaVisita` la use como `ProximaCita`=`ProximoElegibleDesde` (cita y próxima elegibilidad son la misma fecha) y `AppointmentSeeder` agende la cita real. Tested in `SeguimientoPolicyTests`.
- **Citas reales (Bahmni Appointments / agenda O3)**: `AppointmentSeeder` materializa el follow-up como cita en la agenda. `SeedAsync` (tras la consulta) hace `POST /appointment` con `patientUuid`, `serviceUuid` (`Defaults.AppointmentServiceUuid`, vacío = feature off), `serviceTypeUuid` opcional, hora realista (slots 15 min, 08:00–15:45), el **médico/consultorio reservados para el control** (`ProximaCitaProviderUuid/LocationUuid` — el mismo que atenderá esa visita, ver *Coherencia de la consulta de seguimiento*; fallback al de la visita actual) y `comments=SEEDED_BY_SIMULATOR`; el UUID va a `SimulatedPatient.CitasPendientes` (lista compartida por referencia con recurrentes, como `ProblemListConcepts`). `ResolverCitasAsync` (al llegar cada visita) usa el seam puro `ClasificarCitas(citas, fechaVisita, Appointments.ToleranciaDias)` (def. 3): cita a ±tolerancia → `Completed` (vino a su cita); anterior a la ventana → `Missed` (no-show realista); futura → queda. ⚠️ La transición usa el recurso **plural** `POST /appointments/{uuid}/status-change` (el de creación es singular). **Sweep de cierre**: al terminar los días, `SweepMissedAsync(pool, EndDate)` marca `Missed` toda cita anterior a `EndDate − tolerancia` (seam puro `CitasVencidas`) — invariante verificado: 0 `Scheduled` vencidas al cierre. **`clear` cancela** las citas `Scheduled`/`CheckedIn` del paciente antes de voidearlo (`POST /appointments/search` con `{patientUuid, startDate}` — startDate es obligatorio). Servicios verificados en esta instancia: General Medicine service `7ba3aa21-…` + tipo "Short follow-up" `fbec4378-…`. Testeado en `AppointmentSeederTests`. **QA en BD**: `querys/coherencia_seguimiento.sql` audita las invariantes del control (mismo médico / mismo dx / 0 `Scheduled` vencidas). ⚠️ El módulo inserta `patient_appointment_provider.voided` como **NULL**, no 0 — filtrar con `voided = 0` deja fuera todas las filas y parece (falsamente) que las citas no tienen médico; usar `COALESCE(voided, 0) = 0`.
- **Resultados de laboratorio (ciclo orden→resultado)**: `LabOrderSeeder` captura el UUID de la orden (`POST /order`) y registra el resultado como **obs ligada a la orden** (`POST /obs` con campo `order`), coherente con la enfermedad. Seam puro `LabResultGenerator.Generar(lab, categorías, dxUuids, rng)`: **numérico** → banda normal (`res_min..res_max`) o anormal (`res_min_anormal..res_max_anormal`) si el paciente tiene una categoría de `res_trigger`; **codificado** → `res_normal_uuid` (p.ej. Negativo) vs `res_anormal_uuid` (Positivo), disparado por diagnóstico específico `res_trigger_dx` (p.ej. dengue→NS1 Positivo); **imagen/vacío** → sin resultado (la orden queda sola). **Paneles (obs-group)**: `datatype=panel` busca sus componentes en `catalogs/paneles.csv` (`panel_uuid,componente_uuid,nombre,res_min/max,res_min/max_anormal,res_trigger`) — hoy el hemograma `1019…` con Hb/Hto/leucocitos/plaquetas — y postea **una obs padre** (concepto del panel, ligada a la orden) **+ una obs hija por componente** (`groupMembers`). Seam puro `LabResultGenerator.GenerarComponentes`: cada componente sortea SU banda de forma independiente según `res_trigger` (infeccioso→plaquetas bajas/leucocitos altos; digestivo→anemia). Panel sin componentes catalogados (lipídico, orina…) = orden sola, como antes. `ReferralProbabilities.LabResult` (def. 0.90) = fracción que "vuelve" con resultado el mismo día; **el resto se difiere de verdad**: el valor se genera con el contexto clínico de la visita que lo ordenó, queda en `SimulatedPatient.ResultadosPendientes` (lista compartida por referencia, como `CitasPendientes`) y `LabOrderSeeder.ProcesarPendientesAsync` (llamado en cada visita, antes de las órdenes nuevas) lo registra en la **siguiente visita** del paciente ligado a la orden original ("ya llegó el resultado"; si no vuelve, la orden queda pendiente para siempre — realista). **Precisión**: banda con límites enteros → valor entero (conceptos con `allow_decimal=false` como ASAT `653…`/amilasa `1299…` rechazan decimales con `Obs.error.precision`; un entero siempre es válido); bandas decimales (HbA1c, Hb) conservan 1 decimal. Imágenes siguen sin resultado. Testeado en `LabResultGeneratorTests`.
- **Roster diario de médicos (2-3/día)**: `Simulation.MinMedicosPorDia`/`MaxMedicosPorDia` (def. 2/3). Seam puro `ClinicResourceAssigner.SeleccionarActivos` + `ActivarMedicosDelDia(fecha)` (llamado 1×/día desde `SeedOrchestrator.RunAsync`) fija qué médicos "abren consultorio" ese día (subconjunto del pool de `consultorios.csv`). El roster es **determinista por fecha** (`RosterDe(fecha)`: RNG sembrado con `RandomSeed + 18 + fecha.DayNumber`, memoizado), no una tirada del RNG de la corrida — así, al agendar una cita, se puede consultar HOY el turno del día futuro y reservarla con un médico que efectivamente atenderá (ver *Coherencia de la consulta de seguimiento*). `AssignVisit` condiciona el médico de cabecera a que esté disponible ese día (si no, el paciente cae con otro sin perder su cabecera). Pool ≤ Min = todos disponibles (sin efecto). Testeado en `ClinicResourceAssignerTests`.
- **Coherencia de la consulta de seguimiento (mismo médico + mismo dx)**: antes, el paciente que acudía a su cita de control se topaba con un **médico re-sorteado** (`AssignVisit` ignoraba el provider de la cita → la cita quedaba `Completed` firmada por un médico y el encounter de ese día por otro) y, en un control crónico, con **una crónica al azar** de las que arrastra (un HTA+DM2 "iba a su control" de la otra condición). Ahora **la cita transporta el motivo y el médico**: `SimulatedPatient.MotivoProximaCita` (dx primario de la visita que la agendó) + `ProximaCitaProviderUuid`/`ProximaCitaLocationUuid`, fijados en `FijarProximaVisita` junto a `ProximaCita` (y puestos a `null` cuando no hay seguimiento). El médico se reserva antes de postear la cita (`ClinicResourceAssigner.ReservarCita` en `ProcesarVisitaAsync`, entre la consulta y `AppointmentSeeder`) con el seam puro `ElegirMedicoCita`: prefiere (1) el médico de la visita actual si estará de turno esa fecha (`RosterDe`) — el que ordena el control es quien lo da —, si no (2) la cabecera si está de turno, si no (3) uno del roster; roster vacío = médico actual (modo proveedor único intacto). Al volver el paciente, `SeedOrchestrator.DxDeControl` (seam puro) da prioridad a la cita: si `RecurrentSelector.TieneCitaHoy` (±`Appointments.ToleranciaDias`, seam compartido con la selección de recurrentes) y hay motivo → **ese** es el dx (sin tirar dados) y `AssignVisit(patient, citaRecursos)` honra el médico reservado sin re-sortear (un médico entra a atender las citas que tiene reservadas, aunque ese día no le tocara roster). Sin cita (retorno de relleno, o llegada fuera de tolerancia) se conserva **intacta** la lógica probabilística previa (`RollSeguimientoCronico` → episodio agudo vigente + `RollSeguimientoAgudo`). Testeado en `SeedOrchestratorTests` (`DxDeControl`), `ClinicResourceAssignerTests` (`ElegirMedicoCita`), `RecurrentSelectorTests` (`TieneCitaHoy`).
- **Vitals coherentes con la enfermedad**: `VitalsSeeder.ComputeVitals` es un **seam puro estático** (testeado en `VitalsSeederTests`) que deriva 8 obs de la **unión de categorías** del paciente (`patient.Categorias`, incluye comorbilidades — no solo el primario) + la **peor severidad** de `TodosDiagnosticos`. Reglas: peso **acoplado a la talla vía IMC** (objetivo 27–38 en diabetes/endocrino o `vital_imc=alto`; 16–19 en `vital_imc=bajo`; 18.5–27 normal; banda infantil para 0-14) → no más IMC absurdos; fiebre 37.5–40 si `infeccioso`/`respiratorio≥moderado`/`vital_fiebre`; taquicardia con fiebre; taquipnea en respiratorio/infeccioso; SpO2 por severidad respiratoria; HTA en cardiovascular. **Continuidad física**: la talla se fija en la primera visita (`SimulatedPatient.TallaCm`) y es constante entre visitas; el peso deriva poco alrededor de `ImcBasal` (también fijado en la 1ª visita) salvo override de enfermedad; el grupo 0-14 usa talla por **edad en meses** (`VitalsSeeder.TallaPediatricaCm`, no la banda plana 90–160). Los parámetros nuevos de `ComputeVitals` (`tallaFijaCm`, `imcBasal`, `edadMeses`) son opcionales — con `null` el comportamiento es idéntico al histórico. El `AgeGroup` del recurrente se **recalcula** a la fecha de la visita con `PatientProfileGenerator.GrupoEdad(birthDate, fecha)` (la edad avanza con el tiempo simulado). Tested in `AntropometriaEdadTests`.
- **Vitals — SpO2 vs frecuencia respiratoria**: ⚠️ El SpO2 va al concepto `5092` (no `5242`, que es *frecuencia respiratoria*). Se emiten **ambas**: FR real en `5242` (12–20, elevada en respiratorio/infeccioso) y SpO2 en `5092` (95–99, baja 88–93 en respiratorio grave). La query `querys/visita_detalle.sql` §5 (QA) caza valores imposibles (p.ej. FR>40).
- **Pistas de vitales por enfermedad (opcionales)**: columnas `vital_fiebre` (bool), `vital_imc` (`alto`|`bajo`), `vital_pa` (`alta`), `vital_fc` (`alta`|`baja`) y `vital_spo2` (`baja`) en `diagnosticos.csv` permiten **override por enfermedad** sobre la lógica de categoría (p.ej. *hipertiroidismo* es endocrino pero adelgaza y taquicardiza → `vital_imc=bajo`+`vital_fc=alta`; *preeclampsia* es ginecoobstetrico pero hipertensa → `vital_pa=alta`; *insuficiencia cardíaca* desatura → `vital_spo2=baja`; *hipotiroidismo* bradicardiza → `vital_fc=baja`, y gana incluso sobre la taquicardia febril). El override gana sobre la categoría. Ausentes/vacías = neutro; el `CatalogLoader` las parsea de forma retrocompatible. Pobladas por reglas de keywords en `scripts/ajustar_diagnosticos.ps1` (~35 pa / ~48 fc / ~11 spo2; `fetal` excluido de fc — la taquicardia fetal no es el pulso de la madre; la anemia NO baja la SpO2, solo da `vital_fc=alta`). Tested in `VitalsSeederTests`.
- **Visit closing**: `VisitCloseSeeder` runs last in `ProcesarVisitaAsync` and sets `stopDatetime` (1–4 h after arrival) via `POST visit/{uuid}`. Encounters (vitals/consulta) are point-in-time (`encounterDatetime`) and have no open/closed state — only the **visit** is closed.
- **Person attributes (teléfono + estado civil)**: `PatientProfileGenerator` genera para cada paciente nuevo un teléfono salvadoreño sintético (seam puro `GenerarTelefono`: móvil `7###-####` ~80 % / fijo `2###-####` ~20 %; en menores es el contacto del tutor) y un estado civil **coherente con la edad** (seam puro `GenerarEstadoCivil(edad, rng)`: <18 siempre soltero; con la edad crece casado/acompañado; viudez visible en 65+; UUIDs = answers del concepto CIEL `1054` verificados en esta instancia, constantes `EstadoCivil*` del generador). `PatientSeeder` los anida como `attributes:[{attributeType,value}]` en el `person` del `POST /patient` — el value de Civil Status es el **UUID del answer** (attribute type formato Concept). Config `Defaults.TelephoneAttributeTypeUuid`/`CivilStatusAttributeTypeUuid` (vacío = feature off, patrón `AppointmentServiceUuid`). ⚠️ `GET /concept?q=…` con custom rep de `answers` da NPE en esta instancia — pedir el concepto por UUID con `v=full`. Tested in `PatientProfileGeneratorTests`.
- **Realistic patient names (catalog-driven, 2 given + 2 family)**: `PatientProfileGenerator.GenerateNew` builds the name from catalogs `nombres.csv` (`nombre,genero`) and `apellidos.csv` (`apellido`) — **primer + segundo nombre** (distinct, gendered) and **primer + segundo apellido** (distinct). `PatientSeeder` sends them as `givenName`/`middleName`/`familyName`/`familyName2`. This fixes the old bottleneck where Bogus locale `"es"` `FirstName(gender)` yielded only ~24 distinct first names → ~1.800 patients sharing a full name over a 1-year run. Pools are cached lazily in the generator (CatalogLoader loads after ctor). **Fallback**: empty `nombres.csv`/`apellidos.csv` → old Bogus single-name behavior (`SecondGivenName`/`SecondFamilyName` empty), so tests/back-compat are unaffected.
- **Longitudinal continuity (chronic patients return for the same condition)**: `SimulatedPatient.CronicasActivas` accumulates the patient's `EsCronica` diagnoses (deduped by UUID, written back to the **pool** object via `SeedOrchestrator.RegistrarCronicas`, shared like `ProblemListConcepts`). On a recurrent visit, if the patient carries ≥1 chronic dx and the pure seam `EpidemiologySelector.RollSeguimientoCronico(Simulation.SeguimientoCronicoProb)` (default 0.70) fires, the visit's **primary dx = one of their chronic conditions** (control visit) instead of a fresh random acute complaint; category follows the chronic dx. Otherwise the previous fresh-random selection is kept. **On a chronic control the problem list is stable**: comorbidities are the patient's *other* known `CronicasActivas` (not freshly rolled each visit — that made the list grow unbounded, A9); acute visits still layer fresh comorbidities via `SelectComorbilidades`. Combined with repeatable orders (below), a chronic returns control-after-control with the same dx, same labs and same drug.
- **Acute follow-up coherence (mirror of chronic continuity, for non-chronic returns)**: before, a non-chronic patient returning in 7–21 days got a **fresh random dx** (pneumonia → returns with dermatitis — incoherent, and worse now that they arrive at their *scheduled appointment*). `SimulatedPatient.UltimoDxAgudo`/`FechaUltimoDxAgudo` track the open acute episode (set on every visit whose primary dx is non-chronic, via `SeedOrchestrator.RegistrarEpisodioAgudo`; pool object only). On a recurrent visit, if the chronic-control branch didn't fire and the pure seam `EpidemiologySelector.EpisodioAgudoVigente(fecha, day, Simulation.VentanaSeguimientoAgudoDias)` (default 30 d) holds and `RollSeguimientoAgudo(Simulation.SeguimientoAgudoProb)` (default 0.70) fires → **primary dx = the same acute dx** (control/mejoría). The control visit **closes** the episode (no infinite same-dx loops); a chronic-control visit doesn't touch it (expires by window). Measured effect: same-dx share on consecutive visits went from **2.3% → 64.2%** (Feb vs Mar 2025 runs). Tested in `EpidemiologySelectorTests`.
- **Sex-coherent diagnoses**: `EpidemiologySelector.SelectDiagnostico` hard-filters candidates by `DiagnosticoEntry.Sexo` (`M`|`F`|`""`=ambos) so a male never gets a pregnancy/eclampsia dx and a female never gets a prostate dx. Before, harvested rows carried `peso_M=peso_F` and the selector only *weighted* by sex (never excluded), so incoherent picks slipped through. The `sexo` column in `diagnosticos.csv` is populated by keyword rules in `scripts/ajustar_diagnosticos.ps1` (`$sexoF`/`$sexoM`, accent-insensitive, idempotent; only sets when empty). Empty = both.
- **Spanish concept names (CIEL localization)**: some CIEL concepts used as diagnoses had **no `es` name in this instance**, so the Spanish UI showed them in English ("Heart failure", "Dengue with warning signs"). `scripts/agregar_nombres_es.ps1` pushes each catalog `nombre_es` as a locale-preferred **synonym** (`POST /concept/{uuid}/name`, additive/idempotent — never deletes) so they render in Spanish; UUIDs/CIEL codes are unchanged. 12 redundant English-only concepts that duplicated an existing Spanish-named concept were **repointed** in the catalog to that concept's UUID (no disease lost). Also resolved 3 rows that had `ciel_uuid=PENDIENTE`. Run `pwsh scripts/agregar_nombres_es.ps1` against a fresh instance to re-apply.
- **Realistic inter-visit spacing + agenda governs return**: a patient cannot return day-after-day. Each pool patient carries `SimulatedPatient.ProximoElegibleDesde`, set after **every** visit (in `SeedOrchestrator.FijarProximaVisita`, after `RegistrarCronicas`): if the consulta scheduled a follow-up, `ProximaCita = ProximoElegibleDesde = FechaSeguimiento` (same date); else only the min interval from `RecurrenceScheduler.ProximaFechaElegible(lastVisit, esCronico, rng, Simulation.Recurrence)` (chronic 30–120 d / acute 7–21 d) and no `ProximaCita`. **Recurrent selection** no longer picks at random: the pure seam `RecurrentSelector.Seleccionar(elegibles, fecha, cupo, ToleranciaDias, Appointments.AsistenciaProb, rng)` attends patients **with a cita for today (±tolerance) first**, each with attendance prob (no-shows don't get pulled into the random fill — their cita later goes Missed), then fills the remaining quota randomly. Eligibility filter = not attended today AND `day.Date >= ProximoElegibleDesde`. **A11**: quota not covered by eligible recurrents is filled with new patients (`CrearYProcesarNuevoAsync`) instead of lost. Tested in `RecurrenceSchedulerTests`, `RecurrentSelectorTests`.
- **Salvadoran addresses (catalog-driven, clinic in San Salvador)**: `catalogs/direcciones.csv` (`departamento,municipio,zona,peso`) — one row per colonia/barrio/cantón. `PatientProfileGenerator.GenerateAddress` picks a row by weight. ## OpenMRS REST API Constraints (Learned from Validation)

- **Diagnoses**: must go in `encounter.diagnoses[]` field, NOT as separate obs. Fields required: `rank` (int, NOT NULL — `1` for primary, `2` for secondary/comorbidities), `certainty` (`CONFIRMED` or `PROVISIONAL`, NOT `PRESUMED`), `diagnosis.coded` (concept UUID). A single encounter may carry multiple diagnoses (comorbidity) — `ConsultaSeeder` emits `patient.TodosDiagnosticos` (primary rank=1 + each comorbidity rank=2).
- **Order urgency**: valid values are `ROUTINE`, `STAT`, `ON_SCHEDULED_DATE`. `URGENT` is NOT valid.
- **DrugOrder (dosing type "simple")**: must send `concept` (concept UUID, separate from `drug`), `quantity`, `quantityUnits`, `frequency`, `route`, `dose`, `doseUnits`. Posology is catalog-driven with fallback: optional `medicamentos.csv` columns `dosis`, `unidad_dosis_uuid`, `frecuencia_uuid`, `dias_tratamiento` (empty = 1 tablet / once-daily / 7-14-30 d, the `Defaults.*`). Verify frequency/dose-unit UUIDs against the instance (`GET /orderfrequency`, `GET /concept?q=`).
- **Repeatable orders by validity date (`OrderedConcepts`)**: `SimulatedPatient.OrderedConcepts` is a `Dictionary<conceptUuid, DateOnly vigenteHasta>` (was a permanent `HashSet` block). Lab/drug seeders skip a concept only while an order is still active at the visit date (pure seam `OrderVigencia.EstaActivo`): test orders carry `autoExpireDate = FechaConsulta + Orders.LabVigenciaDias` (def. 7), drug orders expire by their `duration`. Past that, a chronic control re-orders the same HbA1c / metformina without OpenMRS's `AmbiguousOrderException` (which only rejects two *active* orders of the same orderable). Shared by reference across recurrent visits. Tested in `OrderVigenciaTests`.
- **Obs timing vs encounter (`ConsultaSeeder.FechaConsulta`)**: obs attached to the consultation encounter (chief complaint, clinical exam, return-visit date, lab results/panels) are dated with `FechaConsulta(patient)` (arrival + 30 min = the encounter datetime), never the arrival time — OpenMRS rejects obs earlier than their encounter.
- **Visit overlap**: if `visitCannotOverlapAnother` is returned, fetch existing active visit via `GET visit?patient={uuid}&includeInactive=false` and reuse its UUID.
- **Condition (problem list)**: `POST /condition` — `condition.coded` must be a **plain UUID string** (e.g. `condition: { coded: "uuid" }`), NOT a nested object (sending an object → `LinkedHashMap cannot be cast to String`). Other fields: `patient` (uuid string), `clinicalStatus` (`ACTIVE`|`INACTIVE`|`HISTORY_OF`), `onsetDate`. **To query a patient's conditions use `GET /condition?patientUuid={uuid}`** — `?patient=` returns empty. `ConditionSeeder` adds diagnoses flagged `cronica=true` to the problem list.
- **Allergen format**: `POST /patient/{uuid}/allergy` — `allergen.codedAllergen` must be a **plain UUID string** (e.g. `"codedAllergen": "uuid-here"`), NOT a nested object `{"uuid": "..."}`. Using an object triggers `ResourceDoesNotSupportOperationException` in `ConceptResource1_8`. `severity` and `reactions[].reaction` accept `{uuid: "..."}` normally.
- **Program enrollment**: `POST /programenrollment` — `{ patient, program, dateEnrolled, location, states:[{ state:"<workflowStateUuid>", startDate }] }`. `state` must be a **plain UUID string** (not `{uuid}`) and must belong to the program's workflow. Enumerate programs with `GET /program?v=full` (→ `allWorkflows[].states[]`). `DELETE /programenrollment/{uuid}` **voids** (204); `?purge=true` returns **500** when a `patient_state` FK exists — use void.
- **Appointments (Bahmni module — the one in O3; legacy `appointmentscheduling` is NOT installed, 404)**: create with `POST /appointment` (singular) — `{ patientUuid, serviceUuid, serviceTypeUuid?, startDateTime, endDateTime, appointmentKind:"Scheduled", providers:[{uuid,response:"ACCEPTED"}], locationUuid, comments }`. Status transitions use the **plural** resource: `POST /appointments/{uuid}/status-change` with `{ toStatus, onDate }` (`/appointment/{uuid}/status-change` → Unknown resource). Valid target statuses: `CheckedIn|Completed|Cancelled|Missed`; transitions are validated — e.g. `Completed → Cancelled` is rejected (`Appointment status can not be changed…`). List services: `GET /appointmentService/all/default`. Read by date: `GET /appointment/all?forDate=…`.
- **Order `dateActivated`**: if omitted, OpenMRS stamps the order with the **real server clock** — every simulated order was dated the day of the run, not the visit day (all pre-jul-2026 data has this skew). Both order seeders now send `dateActivated`. Constraint: it **cannot be before the associated encounter's datetime** (`Order.error.encounterDatetimeAfterDateActivated`) — the consulta encounter is at `VisitDatetime + 30 min`, so orders must use that same instant (shared helper `ConsultaSeeder.FechaConsulta`).
- **Numeric obs precision**: concepts with `concept_numeric.allow_decimal=0` (e.g. ASAT `653…`, Amilasa `1299…`) reject decimals with `400 Obs.error.precision`. Round to integer when the concept disallows decimals (open issue in `LabResultGenerator`/`laboratorios.csv`).
- **Obs on N/A-datatype concept → "Don't know how to handle ZZ"**: posting an obs *value* against a concept whose datatype is N/A (HL7 code `ZZ`) fails with `400 value on class org.openmrs.Obs`. Real case: TSH was cataloged as `85077…` which in THIS instance is the **Drug-class** TSH concept (datatype N/A) — the *test order* succeeded (orders don't need a datatype) but every result obs failed. Correct lab concept: `161505…` "Prueba de la hormona estimulante de la tiroides" (Numeric/Test). When verifying catalog UUIDs, check **datatype + conceptClass**, not just the name.
